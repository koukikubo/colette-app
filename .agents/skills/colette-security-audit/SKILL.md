# Colette セキュリティ監査

ユーザーが実装する前提で、監査結果と改善案を返す。修正、Issue作成、コミット、外部サービスへの書き込みは明示依頼時に行う。GitHub側Codexのコードレビューと併用し、差分外の共通処理や設定も必要な範囲で追う。

## 調査の進め方

Docs/development-harness.md、Docs/application-specification.md、Docs/development-environment.mdを読み、git statusと対象commitを確認する。対象機能、調査範囲、利用者の権限、外部入力と信頼境界を把握する。全体監査では認証・共通API・個人情報を扱う経路を優先する。

画面/feature API → Next route/proxy → Rails route/controller → service/model → serializerとDBを追い、攻撃者が制御できる入力が権限確認やデータアクセスへどう到達するか確認する。文字列検索や危険そうなAPIの存在だけで脆弱性と断定しない。

## 確認観点

- 認証・認可: 未ログインのアクセス、セッション失効、退職・ログイン停止、owner/operator/viewerの操作権限、自己昇格、指定IDの差し替えによる不正アクセス。UIの表示制御とサーバーの認可を区別する。
- 入力と出力: SQLの組み立て、HTML出力とエスケープ、外部URLへのアクセス、ファイル・パス・コマンド入力、強いパラメータ、意図しない属性更新。利用中の保護機構と入力の到達可能性まで確認する。
- セッションと通信: Cookie属性、CSRF、CORS、Origin/Hostの扱い、TLS終端、proxyのCookie・ヘッダー転送、認証情報を含むレスポンスのキャッシュ。
- 情報漏えい: 顧客情報、担当者のログイン情報、API返却項目、例外・ログ・テスト成果物、秘密情報の保存と読み込み。秘密値は出力せず、必要ならファイルと変数名だけを示す。
- 可用性と処理整合性: ログイン試行、過大な入力、一覧の無制限取得、重いRF計算やJobの起動権限、再試行と並行処理による不正な状態。通常の業務バグと攻撃に利用できる問題を区別する。
- 依存関係と実行環境: lockfile、Docker、CI、本番設定と脆弱性検査結果。既知の脆弱性は対象版・利用箇所・成立条件を調べる。最新のCVEや修正版が必要なら公式アドバイザリを確認し、確認日と出典を付ける。

## 自動検査と実行確認

.github/workflows/ci.ymlとsecurity.ymlから現在のBrakeman、bundler-audit、npm audit、Trivyの設定と対象を確認する。固定バージョンやコマンドをこのスキルへ複製しない。既存結果を利用できれば先に確認する。
自動検査の指摘とコード上の悪用可能性を照合する。修正版なし・抑制済み・対象外も理由を確認し、検査成功を安全性全体の証明と扱わない。
実行する場合は専用のローカル/test環境を使い、実データを変更しない最小の再現に限定する。本番・外部サービスへの攻撃的スキャン、負荷試験、実アカウントへの試行は通常のコード監査に含めない。

## 監査結果

重大度の高い指摘から報告し、各項目に次を付ける。指摘がなければ無理に作らない。

- 対象ファイルと行、問題の具体的な根拠
- 必要な権限・入力・設定などの成立条件と影響
- 重大度とその理由、確度（確認済み/要追加確認）
- 再現方法または静的な到達経路、改善案と回帰確認方法

設定不足の可能性と実証した脆弱性、既知CVEとアプリでの到達可能性を区別する。CVSS等の数値は根拠なしに作らない。既存IssueやGitHubレビューで同じ指摘がある場合は対応状況を照合し、重複を明示する。
末尾に調査範囲、実行した検査、未実行の理由と残る確認事項を記載する。コードを読んだだけの項目を動作検証済みと報告しない。
