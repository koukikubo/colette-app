# PostgreSQLイメージ内のgosu更新（2026-11-23）

## 対象と修正

`docker/postgres/Dockerfile`でgosu 1.20をビルドするGoを1.27.3から1.27.4へ更新した。PostgreSQLは17.12を維持し、Go開発環境は最終イメージへ含めない。ビルドログへバイナリのGoバージョンを記録する。

対象は`/usr/local/bin/gosu`の標準ライブラリに検出されたCVE-2026-97054。[Go公式アドバイザリ](https://pkg.go.dev/vuln/GO-2026-6859)ではnet/httpの並行処理に起因するパニックで、1.27.4が修正版。gosu経由での攻撃成立を実証したものではない。

再発予防として、DependabotのDocker更新対象に`/docker/postgres`を追加した。Goは1.27系のパッチ更新、PostgreSQLは17系の更新を候補に残す。

## ローカル検証

2026-11-21にlinux/amd64向けイメージを`--pull`付きでビルドし、Trivy 0.70.0（当時のCIと同版）で修正前後を検査した。全深刻度と秘密情報を対象に、同じ更新済み脆弱性DBを使用した。

| 確認項目                   | 修正前 | 修正後 |
| -------------------------- | ------ | ------ |
| gosuのビルド用Go           | 1.27.3 | 1.27.4 |
| CVE-2026-97054             | 1件    | 0件    |
| HIGH・CRITICAL総数         | 123件  | 123件  |
| 修正版のあるHIGH・CRITICAL | 0件    | 0件    |
| 秘密情報                   | 0件    | 0件    |

過去のPR #238のCIでは対象CVEはHIGHだったが、今回のローカルDBではMEDIUMだった。深刻度の変動によるゲート通過と修正を混同せず、対象CVEそのものが消えたことで確認した。残存123件にはスキャナ上の修正版がなく、脆弱性全体の解消や本番利用可能の判定ではない。既存のCI判定・除外設定は変更していない。

修正後の検証イメージは`colette-postgres-security-check:go1.27.4`、IDは`sha256:9e82ec637308efd8b5b37e36cef6ea7f29078bf4cc81eafd489be7a49a6cd378`。

2026-11-23に、通常DBのボリュームを使わない一時コンテナ（network none、PGDATAはtmpfs）で以下を確認した。

- TCP接続可能になるまで待機し、初期化用の一時サーバーを起動完了と誤認しない。
- `gosu postgres id`によるユーザー切替。
- PostgreSQL 17.12の起動、テーブル作成、INSERT、SELECT。
- 検証後に一時コンテナを停止・削除。

前回の起動検証は初期化中の接続切替で失敗していた。上記の再検証成功と区別して扱う。

## 適用範囲

通常利用中の`colette_db`の再作成・データ移行・本番デプロイは行っていない。修正したDockerfileから今後ビルドするイメージが対象であり、既存コンテナへの反映とは別である。GitHub CIとレビューの結果は対応PRで確認する。

## CIで判明した追加対応

PR #240の初回CIでは、Runtime securityの3イメージと実サービスE2Eは成功した。一方、Railsの静的検査は`bin/brakeman`の`--ensure-latest`により、8.1.0が最新8.1.1ではないことを理由に終了コード5で停止した。脆弱性検出による失敗ではない。

検査条件を維持して`backend/Gemfile.lock`のBrakemanのみ8.1.1へ更新した。他のgemの固定版は変更していない。最終コミットのCI・レビュー結果はPRを参照する。

ローカルの更新後BrakemanはDockerのバインドマウント上の`config/puma.rb`読み込みで`Errno::EDEADLK`となり、検査を完了できなかった。最新版の確認は通過したが、静的検査成功とは扱わず、独立したCI環境で再検証する。後続のbundler-auditもこのローカル実行では未実行。
