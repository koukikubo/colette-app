# 手動退店・来店結果訂正（#223）

## 採用仕様

- 予約の自動完了Jobは追加しない。既存の毎日03:00のRF Jobを維持する。
- 受付状態は基本コードマスタの仮予約／予約確定。来店結果は未退店／退店済／通常キャンセル／無断キャンセルとして区別する。
- 仮予約は、確認画面から予約確定と退店を同じトランザクションで記録する。
- 無断キャンセルへの訂正・無断キャンセルからの訂正は理由不要。それ以外の訂正には理由が必要。
- `completed_at` は退店処理を記録した日時。実際の退店時刻として扱わない。予定開始／終了日時を時計に合わせてDB更新しない。
- 予定終了を過ぎた未退店予約は、予約管理の未処理一覧から確認する。ダッシュボードへ個別一覧を追加しない。

## 保存と互換性

`cancellation_kind` は通常取消 `regular`、無断取消 `no_show`、既存取消の種別不明 `unknown`。旧データの日時は保持し、種別を推測しない。結果は既存日時から導出し、受付状態へ混ぜない。

`reservation_result_changes` に変更前後、担当者、理由、操作、記録日時を保存する。既存の認証監査とは分離する。操作の再送キーと入力ダイジェストも同じ記録へ保存する。顧客・日時・人数の訂正は専用APIで結果と一体保存し、通常更新からの実績変更を拒否する。

旧完了／解除／取消／復元APIも共通サービスを経由する。全結果更新で `Idempotency-Key` と `lock_version` が必要。解除／通常取消の復元は、訂正と同じ理由条件を適用する。既存クライアントと同時に更新する必要がある。

同一担当者・同一キー・同一操作の再送では更新も監査も増やさず、現在の予約を返す。キーを異なる内容へ再利用すると409。書込ロック→行ロック→提出版の検証の順で、古い版を409で拒否する。取消から戻す際は席・顧客の競合を再検証する。

## 移行・切戻し

追加migrationは取消区分と監査テーブルを作成する。通常の開発DBへの適用前には、対象DBを確認してバックアップを取得する。旧取消は `unknown` として移行する。過去の未退店予約を一括完了しない。

監査を作成した後に `db:rollback` すると履歴テーブルを失う。稼働後は安易にrollbackせず、データを保存して前進修正する。認証・CSRF・予約登録の再送対策は維持する。
