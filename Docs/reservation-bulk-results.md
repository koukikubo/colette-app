# 予約の選択一括処理

## 操作と整合性

未処理一覧は表示日の予定終了済み予約だけを表示する。「表示日分を全選択」「過去分を含めて全選択」は選択だけを行い、来店実績を自動確定しない。処理内容は未選択で開始し、退店・通常キャンセル・無断キャンセルから選んで対象予約を確認する。表示日とは画面の日付で、初期値は店舗の今日。

全選択はページングされた既存一覧APIを取得する。途中の取得失敗・件数変化・重複による不足は全選択の成功として扱わない。以前の選択を保持して再試行を案内する。選択中も予約の更新をロックせず、確定時に選択時点の `lock_version` で検証する。

保存は各予約の既存APIを順番に呼び出す。予約単位のトランザクション・認可・CSRF・監査・冪等性を維持し、一括全体を一つの保存とは扱わない。成功・失敗・結果未確認・未送信を予約ごとに表示する。409等の拒否は選び直し、通信結果が不明な予約と未送信分だけを同じ本文・版・キーで再試行する。結果未確認中は別の一括操作へ切り替えず、確認画面を閉じても同じ操作を再開できる。仮予約の退店には受付確定の確認チェックが必要。

## 契約と更新

`GET /api/v1/reservations?state=pending_checkout&date=YYYY-MM-DD` は店舗日付で限定する。日付なしは従来どおり全期間の未処理。レスポンスと更新APIの基本形式は維持する。結果更新で保存済みキー照合後に版競合を検出した場合は、409に `code: reservation_result_conflict` を付け、未保存が確定した競合として選び直せるようにする。認証・CSRF拒否だけでは以前の保存結果を断定しない。新規DB項目・Job・専用一括保存APIは追加しない。

新規予約は基本コード `confirmed` を初期値にする。有効なコードがなければ別コードを推測せず未選択とする。30秒再取得とフォーカスによる定期取得のフックを予約一覧から外し、保存後のイベント・日付変更・手動更新を維持する。実入店を断定せず予定からの経過を表示する1分時計は維持する。他端末の変更は手動取得する。

## 検証

RSpecで表示日／全期間の取得、既存の状態変更・同時操作・再送・監査を確認する。Vitestで選択だけでは保存しないこと、未選択行の不変、仮予約確認、viewer制御、全ページ取得、競合・通信断の部分結果と同じキーによる再試行、予約確定の初期値、30秒取得の停止を検証する。専用E2E環境では画面から一括取消・全期間選択・仮予約確認・一括退店と応答喪失後の復旧を通し、PC・390px画面を撮影する。通常の開発DBをE2Eに使用しない。
