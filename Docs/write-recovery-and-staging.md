# 登録の再送回復とクライアント確認環境

## 変更と契約

顧客POSTも予約と同様にIdempotency-Keyを必須にする。同じ担当者・同じキー・同じ入力は同じ顧客/予約を返し、異なる入力の再利用は409。名前等の一致を使って別の正当な顧客登録を禁止しない。顧客本体と再送履歴は同じtransactionで保存する。独立接続の並行再送をDBロックで直列化する。

GET `/api/v1/customers/creation_result` と `/api/v1/reservations/creation_result` は同じヘッダーキーで本人の確定済み結果だけを返す。未確認は404/code=creation_not_found。まだ届いていない要求があり得るため、404でもキーを捨てない。結果確認は書き込みを再送しない。

同じタブのsessionStorageへ担当者別のランダムキーだけを保存し、入力本文・顧客情報は永続化しない。リロード後はGETで結果確認し、結果が見つからない場合は元の入力を再入力して同じキーで明示的に再送する。画面内に元の本文があれば「前回の内容で再試行」を使う。ブラウザーの保存領域が利用できない場合はPOSTを送らない。タブを閉じてsessionStorageが破棄された場合や別端末への引継ぎは対象外であり、永続的な下書き保存を実装済みとは扱わない。

APIのHTTP成功だけでは保存成功としない。JSONの成功envelopeと登録結果のIDを確認する。要求と本文読取は35秒で中断し、タイムアウトや通信切断の後に書き込みを自動再送しない。Basic認証の401は既存担当者セッションの失効とは区別する。

## 適用

1. DBのバックアップを取り、新規customer_creation_requestsのmigrationを実行する。
2. RailsとNextを同じ対応版へ更新する。旧顧客作成クライアントはキーを送らないため、利用中の画面も更新する。
3. 同一キー再送・異なる入力・同時再送・他担当者のキー・部分保存防止を確認する。

今回のローカルDB準備と検査は専用colette_write_recovery_testで行い、通常の開発DB・本番DBは変更しない。

## クライアント確認環境（未実施）

Oracle環境・公開URL・HTTPS/Basic入口は未用意。#161/#189の受入として、配置先決定後に以下を実施する。CIの専用test環境をこの受入の代替にしない。

- HTTPS・Basic認証後に既存の担当者ログインで利用でき、APIを直接開いてもBasic認証を迂回できない。
- Rails/DB/workerをインターネットへ公開しない。Basicパスワードは設定ファイルやGitへ保存せず秘密管理へ置く。
- Basicの認証失敗と担当者の失効をそれぞれ発生させ、入力保持・再認証・権限を確認する。
- ダミーデータでDB保存後の成功応答だけを失わせ、再試行・リロード後も顧客/予約が一件であることを照合する。
- 保存後の一覧GET失敗、35秒の期限、異常HTML応答、同時編集409、422修正後の再送を確認する。
- 日次03:00のscheduler/worker、失敗の検知、バックアップ復元と切戻しを検証する。
- MFAと実顧客情報を使う実運用の条件はクライアントと別途確定する。

CIのwrite-recovery.e2e.tsは実Railsのcommit後に応答だけを遮断/破損させる。顧客は再取得後の件数まで照合する。Basic認証・Oracleでの検証は含まない。
