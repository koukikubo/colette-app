# 固定RF履歴の顧客内訳の受入（#164）

## 範囲と既存実装

調査基準はmain `76e7a44`。一般顧客検索#143/#224と区別し、選択したRF履歴・条件で内訳を固定する。DBや保存済みRF結果は変更しない。退店仕様#223、顧客詳細タブ#225、共通UI刷新は本件に含めない。

PR #194（merge `609b2c1`）・#196（merge `9faeab5`）と、内訳導入`80f1b5b`・条件と戻り先の整備`d9adff4`・型契約`fe492da`を照合する。現在の内訳はArelのJOIN・条件式と共通サーバーページングで実装されている。

## 修正した点

- 履歴にないランクIDを0件と扱っていたため、対象履歴の保存済みランク集合で検証する。開始ランクは比較元、終了ランクは対象履歴で別々に検証する。履歴内のランクで正しく0件の場合は空結果のまま返す。
- RFセルはRecency/Frequencyの組で検証し、片方がない場合は明確な400とする。
- 開始・終了ランクだけを指定した条件でも名称を省略しない。無条件の単一履歴は「RFランクが付与された顧客」、比較は「比較履歴に記録された顧客」とし、現在の全顧客とは区別する。
- APIが認めたURLの表示件数（1件等）を選択肢へ含め、実際のページ情報を表示する。
- RF内訳から顧客詳細へ進んだ場合、取得成功・失敗の双方で「RFの顧客内訳に戻る」と案内する。履歴・条件・ページ・元の分析画面の戻り先をURLで維持する。

不正ランク・不完全なセル条件・比較条件名・件数選択・詳細の戻る名称は、変更前に失敗するRSpec/Vitestで固定した。取得失敗を空結果として表示せず、同じ条件で再取得する。

## 履歴の意味

現在の適用先が後続履歴へ変わっても、指定した履歴IDを読み続ける。名称・順位は保存済みランクスナップショットを優先し、最終来店日・回数・Recencyはその履歴の結果行を使う。顧客名・法人名は現在の顧客情報であり、過去の名前を保存したものではない。スナップショットのない旧履歴は既存のマスタ参照へフォールバックするため、失われた過去の名称を復元できるとの保証はしない。

履歴は既存仕様どおり、現在適用中の履歴から辿れる完了履歴に限る。未適用の計算結果を内訳へ混入しない。保存済み履歴・比較・復元のデータは書き換えない。

## 3,000件の実測

専用test DBへ3,000人・2履歴分の結果を一括投入し、別ランクの1人を追加。ランク人数・RFセル・上昇カテゴリそれぞれの集計3,000件と内訳総件数を照合した。ページ30・100件指定で最後の100 IDが一致し、`instantiation.active_record`で顧客の実体化が100件だけであることを確認した。

| 条件         | 単独Request Spec | 全体RSpec・契約採取・Vitest並行時 |
| ------------ | ---------------: | --------------------------------: |
| ランク       |         0.0358秒 |                          1.8767秒 |
| RFセル       |         0.0318秒 |                          0.4054秒 |
| 上昇カテゴリ |         0.0355秒 |                          0.1649秒 |

2026-11-19のローカル計測。amd64 RubyテストイメージをApple Silicon上で実行し、既存の専用test DBを使用。データ作成時間は除き、GETの認証・SQL・描画を含む。負荷・契約採取等で変動する参考値であり、本番の応答時間保証ではない。時間の上限を不安定な回帰テストにせず、取得件数と実体化上限を自動検証する。

再現は専用test DBを明示し、`bundle exec rspec spec/requests/api/v1/rf/customer_breakdown_acceptance_spec.rb`。各条件の実測値はRSpecの出力に記録される。通常の開発DBへの大量データ投入は行わない。

## 実サービス受入

E2EはGitHub Actionsの専用DB・Rails・Nextを使用する。ランク人数とRFセルからの遷移、実APIでの計算/適用後の履歴固定、ページ2と表示件数、顧客詳細・予約履歴・ブラウザの戻る操作、比較条件、通信失敗から再取得、PC/390pxとキーボード操作を確認する。元の来店実績1件と新しい未訪問顧客2名を使い、人数をモックで置き換えない。

全体RSpec/Vitest、実Rails契約、型・Lint・整形・ビルド、実サービスE2E、Codexレビューの結果はPRとIssue #164へ記録する。本番環境の配置・残存指摘への対応は、ユーザー指定どおり後段に回す。
