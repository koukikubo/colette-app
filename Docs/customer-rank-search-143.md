# 顧客一覧の手動ランク・現在RFランク検索（#143）

## 仕様

一覧取得のたびに現在適用中の完了したRF履歴を一度選び、検索・結果表示・選択肢を同じ履歴へ固定する。手動ランクは最新の顧客情報、RFは計算履歴時点の情報として区別する。RFをこの画面で再計算しない。

`GET /api/v1/customers`は既存条件に加えて`rf_rank_id`または`rf_rank_state`を受け付ける。同時指定・不正な分類・適用履歴にないランクIDは400。絞り込みはDBのRelationへページ分割前に適用する。

各顧客に`current_rf_rank`、`rf_rank_state`、`rf_rank_basis`を追加する。一覧の`rf_reference`は`calculation_run_id`・`base_date`・ランク選択肢を返す。作成・更新レスポンスは変更しない。

| rf_rank_state  | 表示                                       |
| -------------- | ------------------------------------------ |
| no_applied_run | 適用履歴なし                               |
| not_calculated | 未計算（適用履歴はあるが顧客の結果がない） |
| excluded       | RF計算対象外                               |
| no_visit       | 来店履歴なし                               |
| unmatched      | ルール未一致                               |
| ranked         | 計算履歴のランク名                         |

N/Rなどの文字から分類を推測せず、除外理由とルールの未訪問ランクIDを使用する。名称・色は履歴スナップショットを優先し、旧履歴だけ既存マスタ参照へフォールバックする。ページ内のRF結果を一括取得し、顧客数に比例したSQL発行を避ける。

## 画面

検索条件とページをURLへ保持する。RF条件を適用・解除すると1ページ目へ戻り、キーワード・手動ランク等の他条件は維持する。詳細リンクに安全な戻り先を渡し、既存の詳細画面の戻り操作で条件を復元する。

一般検索は現在適用中の結果、#164の内訳は指定した過去履歴である。両者を混ぜない。未検索時の一覧非表示・新規ランキング・顧客詳細の再配置は#224/#225へ残す。

## 検証

専用test DBでRequest Spec・全体RSpecと実レスポンス契約を実行する。通常ランク／対象外／未訪問／ルール未一致／未計算、履歴なし、マスタ更新後のスナップショット、旧履歴、不正入力、手動ランクとの複合条件を検証する。3,000件の結果から末尾ページ100件だけ返すことと、ページ人数を増やしてもRF取得SQL数が増えないことを確認する。

Vitestでは条件復元・適用・解除、分類表示、ランクカラー、詳細の戻り先、閲覧専用権限を確認する。実サービスE2Eでは顧客→予約完了→RF適用→顧客一覧検索→詳細→戻ると390px表示を検証する。

Next Linkのクエリ付き遷移は[公式仕様](https://nextjs.org/docs/app/api-reference/components/link)を参照。DB migrationは不要。今回の登録処理は変更せず、未マージPR #209の通信回復を取り込んだものとは扱わない。
